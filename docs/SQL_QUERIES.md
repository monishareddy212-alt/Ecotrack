# EcoTrack — SQL & PostgreSQL DBMS Demonstration Guide

This guide provides beginner-friendly, schema-accurate SQL examples covering core DBMS operations (`CREATE TABLE`, `INSERT`, `SELECT`, `UPDATE`, `DELETE`, `INNER JOIN`, `GROUP BY`, `ORDER BY`, `SUM`, `AVG`, `COUNT`, `HAVING`, `INDEX`) and transaction safety using EcoTrack's real PostgreSQL tables.

> **Important**: Never run destructive demonstration queries (`DELETE`, `DROP`, `TRUNCATE`) against your production Neon database. Run practice queries inside a `BEGIN; ... ROLLBACK;` block or on a local test database.

---

## 1. `CREATE TABLE` — Defining Tables with Constraints

```sql
CREATE TABLE IF NOT EXISTS monthly_goals (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  goal_month DATE NOT NULL,
  target_co2e NUMERIC(14,3) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CONSTRAINT uq_monthly_goals_user_month UNIQUE (user_id, goal_month),
  CONSTRAINT chk_monthly_goals_first_of_month CHECK (EXTRACT(DAY FROM goal_month) = 1),
  CONSTRAINT chk_monthly_goals_target_positive CHECK (target_co2e > 0)
);
```
- **Tables used**: `monthly_goals`, referencing `users`.
- **Why required**: Enforces referential integrity (`user_id`), guarantees a positive numeric budget (`NUMERIC(14,3)`), anchors `goal_month` to the 1st of the month, and prevents duplicate monthly targets per user.
- **Returns**: Creates the relational table and its integrity constraints.

## 2. `INSERT` — Recording a Calculated Carbon Activity

```sql
INSERT INTO activity_logs (
  user_id,
  emission_factor_id,
  quantity,
  calculated_co2e,
  activity_date
)
VALUES (1, 1, 25.500, 3.570000, '2026-11-16')
RETURNING id, quantity, calculated_co2e, activity_date, created_at;
```
- **Tables used**: `activity_logs`.
- **Why required**: Persists a user's activity (`25.5 km` Car Travel × `0.14 kg CO2e/km = 3.57 kg CO2e`) while linking to the exact `emission_factor_id`.
- **Returns**: The newly inserted row's `id`, `quantity`, `calculated_co2e`, `activity_date`, and `created_at`.

## 3. `SELECT` — Selecting the Applicable Emission Factor Version

```sql
SELECT
  id,
  factor_kg_co2e_per_unit,
  source,
  effective_date
FROM emission_factors
WHERE activity_type_id = 1
  AND effective_date <= '2026-11-16'::date
ORDER BY effective_date DESC, id DESC
LIMIT 1;
```
- **Tables used**: `emission_factors`.
- **Why required**: Selects the latest emission factor valid on or before the logged activity date so future factor updates never silently rewrite historical calculations.
- **Returns**: One row containing the factor ID, multiplier, citation source, and effective date.

## 4. `UPDATE` — Updating Activity Quantity and Recalculating Emissions

```sql
UPDATE activity_logs
SET quantity = 40.000,
    calculated_co2e = 5.600000
WHERE id = 10 AND user_id = 1
RETURNING id, quantity, calculated_co2e;
```
- **Tables used**: `activity_logs`.
- **Why required**: Updates an existing record while strictly scoping the `WHERE` clause to `user_id = 1` (preventing cross-user modification).
- **Returns**: The updated record ID, new quantity, and recalculated emissions.

---

## 5. `DELETE` — Removing an Owned Activity Without Affecting Reference Data

```sql
DELETE FROM activity_logs
WHERE id = 10 AND user_id = 1
RETURNING id;
```
- **Tables used**: `activity_logs`.
- **Why required**: Removes a user's activity record cleanly. Because `activity_logs` holds only a foreign key reference to `emission_factors` (`ON DELETE RESTRICT` on the factor side), deleting an activity log never deletes the shared emission factor.
- **Returns**: The deleted activity log ID (`0` rows if not found or owned by another user).

## 6. `INNER JOIN` — Combining Normalized Activity Logs, Factors, and Types

```sql
SELECT
  al.id,
  al.activity_date,
  at.category,
  at.name AS activity_type,
  al.quantity,
  at.unit,
  ef.factor_kg_co2e_per_unit,
  al.calculated_co2e,
  ef.source
FROM activity_logs al
INNER JOIN emission_factors ef ON ef.id = al.emission_factor_id
INNER JOIN activity_types at ON at.id = ef.activity_type_id
WHERE al.user_id = 1
ORDER BY al.activity_date DESC, al.id DESC;
```
- **Tables used**: `activity_logs`, `emission_factors`, `activity_types`.
- **Why required**: Demonstrates 3NF reconstruction—joining three normalized tables to display human-readable category, activity name, unit, and source citation for Activity History and CSV export.
- **Returns**: Complete activity rows sorted newest first.

## 7. `GROUP BY`, `SUM`, `COUNT`, and `ORDER BY` — Category Emission Breakdown

```sql
SELECT
  at.category,
  COUNT(al.id) AS total_activities,
  SUM(al.calculated_co2e) AS total_emissions_kg
FROM activity_logs al
INNER JOIN emission_factors ef ON ef.id = al.emission_factor_id
INNER JOIN activity_types at ON at.id = ef.activity_type_id
WHERE al.user_id = 1
  AND al.activity_date >= '2026-11-01'::date
  AND al.activity_date < '2026-12-01'::date
GROUP BY at.category
ORDER BY total_emissions_kg DESC, at.category ASC;
```
- **Tables used**: `activity_logs`, `emission_factors`, `activity_types`.
- **Why required**: Powers EcoTrack's Dashboard donut chart, Analytics category summary table, and highest-emission category detection directly inside PostgreSQL.
- **Returns**: One aggregate row per active category (`Transportation`, `Energy`, `Lifestyle`) with entry count and total `kg CO2e`.

## 8. `AVG` — Average Carbon Emissions Per Activity Entry

```sql
SELECT
  at.name AS activity_type,
  COUNT(al.id) AS entry_count,
  ROUND(AVG(al.calculated_co2e), 2) AS avg_co2e_per_entry
FROM activity_logs al
INNER JOIN emission_factors ef ON ef.id = al.emission_factor_id
INNER JOIN activity_types at ON at.id = ef.activity_type_id
WHERE al.user_id = 1
GROUP BY at.name
ORDER BY avg_co2e_per_entry DESC;
```
- **Tables used**: `activity_logs`, `emission_factors`, `activity_types`.
- **Why required**: Calculates the arithmetic mean emission per logged entry for each activity type (distinct from the Dashboard's calendar-day average `SUM / elapsed_days`).
- **Returns**: Activity names ordered by highest average emission per entry.

## 9. `HAVING` — Filtering High-Impact Months Above a Threshold

```sql
SELECT
  TO_CHAR(DATE_TRUNC('month', activity_date), 'YYYY-MM') AS month_key,
  COUNT(*) AS activity_count,
  SUM(calculated_co2e) AS monthly_total_kg
FROM activity_logs
WHERE user_id = 1
GROUP BY DATE_TRUNC('month', activity_date)
HAVING SUM(calculated_co2e) > 100.000
ORDER BY DATE_TRUNC('month', activity_date) DESC;
```
- **Tables used**: `activity_logs`.
- **Why required**: Shows the difference between `WHERE` (filters individual rows before grouping) and `HAVING` (filters grouped monthly totals after `SUM()` is computed).
- **Returns**: Only calendar months whose cumulative emissions exceed `100 kg CO2e`.

## 10. `INDEX` — Optimizing Date-Range & Ownership Queries

```sql
CREATE INDEX IF NOT EXISTS idx_activity_logs_user_recent
  ON activity_logs (user_id, activity_date DESC, created_at DESC, id DESC);
```
- **Tables used**: `activity_logs`.
- **Why required**: Speeds up user-isolated monthly analytics queries and Dashboard recent-activity lookups (`LIMIT 5`) without scanning every user's rows.
- **Returns**: Registers a composite B-tree index in PostgreSQL.

## 11. Transactions & Rollback Example (ACID Atomicity)

```sql
BEGIN;

INSERT INTO monthly_goals (user_id, goal_month, target_co2e)
VALUES (1, '2026-12-01', 250.000);

-- Simulate a rollback so no test mutation persists
ROLLBACK;
```
- **Why required**: In EcoTrack, multi-step operations (such as migrations, seeding, and `SELECT ... FOR UPDATE` activity edits in `server/db/connection.ts` `withTransaction()`) execute inside explicit `BEGIN` / `COMMIT` / `ROLLBACK` transactions so partial updates never corrupt database state.

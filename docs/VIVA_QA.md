# EcoTrack — College Viva Preparation & 5-Minute Demo Script

This guide helps you confidently answer faculty questions on DBMS concepts, PostgreSQL design, security, and full-stack architecture, followed by a realistic 5-minute live demonstration script.

---

## Part A: Viva Questions & Beginner-Friendly Answers (24 Questions)

### 1. What is EcoTrack?
**Answer:** EcoTrack is a full-stack web application backed by PostgreSQL that helps users log everyday activities—such as commuting, electricity usage, and cooking gas—and automatically calculates their estimated carbon emissions (`kg CO2e`), displays monthly and daily charts, tracks monthly targets, gives rule-based tips, and exports CSV reports.

### 2. Why did you choose this project?
**Answer:** Sustainability tracking is a practical real-world problem that naturally requires relational database design: multiple users, reusable activity catalogs, versioned emission factors over time, transactionally calculated logs, monthly goal constraints, and SQL analytics (`SUM`, `GROUP BY`, `INNER JOIN`).

### 3. What problem does EcoTrack solve?
**Answer:** Manual carbon spreadsheets break easily, mix up units, lose track of which emission factor was used in past years, and lack user authentication. EcoTrack centralizes conversion factors in PostgreSQL, runs exact server-side calculations, isolates every user's data, and visualizes monthly sustainability progress automatically.

### 4. What is a DBMS?
**Answer:** A Database Management System (DBMS) is software that defines, stores, queries, protects, and manages structured data reliably. It enforces constraints (primary keys, foreign keys, check rules), supports concurrent access, and ensures ACID transactions (Atomicity, Consistency, Isolation, Durability).

### 5. Why did you choose PostgreSQL (and Neon) instead of MongoDB or `localStorage`?
**Answer:** Carbon tracking has structured relationships (`users` -> `activity_logs` -> `emission_factors` -> `activity_types`) and strict decimal financial-like calculations. PostgreSQL gives strong SQL constraints (`NUMERIC(18,6)`, `CHECK`, `FOREIGN KEY`), `GROUP BY` / `DATE_TRUNC` analytics queries, and ACID transactions. Neon provides cloud-hosted serverless PostgreSQL with TLS encryption and zero cost on the free tier.

### 6. What is a relational database?
**Answer:** A relational database organizes data into tables (relations) made of rows (tuples) and columns (attributes), where tables link to each other through shared keys (Primary Keys and Foreign Keys) rather than duplicating data inside one huge file.

### 7. What is a Primary Key?
**Answer:** A Primary Key uniquely identifies every row in a table and cannot be `NULL`. In EcoTrack, all five tables (`users`, `activity_types`, `emission_factors`, `activity_logs`, `monthly_goals`) use auto-generated `BIGINT GENERATED BY DEFAULT AS IDENTITY` `id` columns as their Primary Keys.

### 8. What is a Foreign Key?
**Answer:** A Foreign Key is a column in one table that references the Primary Key of another table to enforce referential integrity. For example, `activity_logs.user_id` references `users(id)` and `activity_logs.emission_factor_id` references `emission_factors(id)`.

### 9. How do the five core tables relate to each other?
**Answer:**
- `users (1)` to `activity_logs (N)` (`ON DELETE CASCADE`)
- `users (1)` to `monthly_goals (N)` (`ON DELETE CASCADE`)
- `activity_types (1)` to `emission_factors (N)` (`ON DELETE RESTRICT`)
- `emission_factors (1)` to `activity_logs (N)` (`ON DELETE RESTRICT`)

### 10. What happens if a user deletes an activity log? Does it delete the emission factor?
**Answer:** No. `activity_logs` only holds a Foreign Key pointing to `emission_factors` with `ON DELETE RESTRICT`. Deleting a log row removes only that user's entry, while shared emission factors remain intact for all other records.

### 11. What is Normalization?
**Answer:** Normalization is the systematic process of organizing database columns and tables to eliminate duplicate data and prevent insertion, update, and deletion anomalies.

### 12. How is EcoTrack normalized up to Third Normal Form (3NF)?
**Answer:**
- **1NF**: Every cell holds a single atomic value (no comma-separated lists), and every table has a Primary Key.
- **2NF**: Every table uses a single-column Primary Key (`id`), so no partial dependency on a composite key is possible.
- **3NF**: Non-key columns depend only on the table's Primary Key (`the key, the whole key, and nothing but the key`). `activity_logs` does not store `category`, `unit`, or `source`—it stores `emission_factor_id`, removing transitive dependencies.

### 13. Why do you still store `calculated_co2e` in `activity_logs` if it comes from `quantity × factor`?
**Answer:** Storing `calculated_co2e` (`NUMERIC(18,6)`) alongside `emission_factor_id` acts as an immutable audit-trail snapshot—just like storing the line-item total on an e-commerce invoice—and allows PostgreSQL `SUM()` analytics queries to aggregate thousands of rows instantaneously.

### 14. What is a `JOIN` (specifically `INNER JOIN` vs `LEFT JOIN`)?
**Answer:** A `JOIN` combines rows from two or more related tables based on matching key columns.
- EcoTrack uses **`INNER JOIN`** (`activity_logs -> emission_factors -> activity_types`) when listing Activity History and CSV exports so every log shows its category, name, unit, and source.
- EcoTrack uses **`LEFT JOIN`** (`monthly_goals` -> `activity_logs`) so a user who set a goal for a month with zero logged activities still sees their goal with `0 kg CO2e` actual emissions.

### 15. What is CRUD?
**Answer:** CRUD stands for the four basic persistence operations: **Create** (`POST /api/activities` -> SQL `INSERT`), **Read** (`GET /api/activities` -> SQL `SELECT`), **Update** (`PUT /api/activities/:id` -> SQL `UPDATE`), and **Delete** (`DELETE /api/activities/:id` -> SQL `DELETE`).

### 16. How are carbon emissions calculated accurately?
**Answer:** On the backend, EcoTrack multiplies `Activity Quantity × Emission Factor` using fixed-point `BigInt` scaled integer arithmetic (`server/utils/carbonCalculator.ts`) instead of binary JavaScript floats, avoiding rounding errors like `0.1 + 0.2 = 0.30000000000000004`, and saves the result in PostgreSQL `NUMERIC(18,6)`.

### 17. What is an emission factor, and where do EcoTrack's factors come from?
**Answer:** An emission factor is a published multiplier measuring `kg CO2e` released per unit of activity (`km`, `kWh`, or `kg`). EcoTrack uses verified sources: India GHG Program (2015) for Car/Motorcycle/Bus, UK DESNZ/Defra (2024) proxy for Metro, Central Electricity Authority (CEA v20.0 FY 2023–24) for India's electricity grid (`0.727 kg CO2e/kWh`), and 2006 IPCC Guidelines for LPG (`2.98463 kg CO2e/kg`). Meal factors are intentionally left unseeded until regional LCA values are configured rather than inventing numbers.

### 18. How does editing an activity protect historical carbon calculations?
**Answer:** When a user edits only the `quantity` of an existing activity, the backend opens a transaction (`SELECT ... FOR UPDATE`), keeps the original `emission_factor_id`, and recalculates using that exact factor—so newer future factor updates never silently change old logs.

### 19. How does user authentication and session management work?
**Answer:** Passwords are never stored in plaintext—they are salted and hashed with `bcryptjs` (cost factor 12). After login, Express regenerates the session ID to prevent session fixation, saves the session inside the PostgreSQL `session` table (`connect-pg-simple`), and sends an `HttpOnly`, `SameSite=Lax` cookie (`Secure` in production) to the browser.

### 20. How is SQL Injection prevented?
**Answer:** EcoTrack never concatenates user input into SQL strings. Every `pg.Pool` query uses parameterized placeholders (`$1`, `$2`, `$3`), so PostgreSQL treats user input strictly as data values rather than executable SQL syntax.

### 21. What other security protections are implemented?
**Answer:** Cross-Site Request Forgery (`X-CSRF-Token`) validation on mutating requests, `express-rate-limit` on auth endpoints, strict `WHERE user_id = $1` row-level ownership checks, CSV formula-injection neutralization (`=`, `+`, `-`, `@`), `x-powered-by` disabled, and security headers (`X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`).

### 22. What is `GROUP BY` and how is it different from `WHERE` vs `HAVING`?
**Answer:** `GROUP BY` collapses rows sharing a common value (like `category` or `DATE_TRUNC('month', activity_date)`) so aggregate functions like `SUM()`, `COUNT()`, and `AVG()` can run per group. `WHERE` filters individual rows **before** grouping, whereas `HAVING` filters whole groups **after** aggregation (e.g., months where `SUM(calculated_co2e) > 100`).

### 23. What is a database transaction?
**Answer:** A transaction groups multiple SQL statements into one atomic unit (`BEGIN` ... `COMMIT` or `ROLLBACK`). If any step fails, `ROLLBACK` undoes all partial changes so the database never enters an inconsistent half-updated state. EcoTrack uses transactions (`withTransaction()`) for migrations, seeding, and locked activity updates.

### 24. How is EcoTrack deployed and what are its main limitations?
**Answer:** EcoTrack deploys as a single Render Node.js Web Service serving the compiled React build (`dist/`) alongside the Express `/api/*` backend connected over TLS to Neon PostgreSQL. Its documented limitations include: unseeded lifestyle meal factors, fixed `Asia/Kolkata` calendar daily average timezone, `5,000`-row CSV export cap, and ~30–50s cold starts on Render's free tier after inactivity.
